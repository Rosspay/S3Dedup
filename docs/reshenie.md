# Описание решения s3-dedup

## Выбранная схема дедупликации

Проект использует content-addressable storage и разделяет logical objects и physical blobs. Logical object — исходный S3 key, с которым работает пользователь. Blob — физическое содержимое, записанное под ключом `<blob_prefix>/<hash>`, например `blobs/84d89877...`. В текущей реализации физическая идентичность определяется парой `(bucket, hash)`, поэтому одинаковые данные внутри одного bucket используют общий blob, а между разными buckets не объединяются.

Для каждого подходящего объекта содержимое читается через `GetObject` и хешируется потоково функцией, принимающей `io.Reader`. Поддерживаются SHA-256 и SHA-512. Listing поступает через `ListObjectsV2` и обрабатывается по мере получения, без сохранения полного списка в памяти. Объекты распределяются между workers; число workers ограничено значением `2 * NumCPU`.

Реализованы два режима. В `report_only` вычисляются хеши и обновляется SQLite cache, но S3 не изменяется. В `pointer` содержимое сохраняется как blob, а исходный key при `delete_originals: true` заменяется JSON pointer object с content type `.json+pointer`. Pointer содержит bucket и key blob, hash, исходный размер и content type. В текущей реализации в pointer переводятся все подходящие original objects, включая первое уникальное содержимое. Это даёт единообразную модель: logical keys содержат только pointers, а реальные данные находятся в blob prefix.

## Cache и подсчёт ссылок

В качестве cache выбран SQLite через драйвер `modernc.org/sqlite`. SQLite хранит две основные таблицы:

- `blobs`: bucket, blob key, hash, size и `ref_count`;
- `objects`: logical bucket/key, ETag, size, last_modified, blob bucket/hash и идентификатор последнего scan.

Primary key blob — `(bucket, hash)`, primary key logical object — `(bucket, object_key)`. Регистрация объекта выполняется за одну SQLite транзакция. Для нового logical object refcount соответствующего blob увеличивается. Если object изменился и теперь имеет другой hash, в одной transaction увеличивается refcount нового blob, уменьшается refcount старого и обновляется object reference.

Перед обработкой cache сравнивает ETag, size и last_modified. Неизменившийся object отмечается как увиденный, отчего повторно не скачивается и не хешируется. После успешного listing `FinalizeScope` находит записи в кеше, которые не встретились в текущем bucket/prefix, удаляет их и уменьшает refcount связанных blobs. Благодаря этому внешнее удаление logical object обнаруживается следующим полным scan.

Кеш сохраняется между запусками и позволяет продолжить работу после restart без полного восстановления состояния с нуля.

## Порядок операций и консистентность

Основное правило — исходный объект нельзя заменять до подтверждения существования blob. В pointer режиме порядок следующий:

1. Object читается потоково, одновременно хешируется и записывается во временный локальный файл.
2. Формируется blobKey.
3. Выполняется `StatObject` для blob.
4. Если blob отсутствует, то содержимое загружается в S3.
5. Проверяется размер созданного или уже существующего blob.
6. Source повторно проверяется через `StatObject`; сравниваются ETag, size и last_modified с состоянием до чтения.
7. Только если source не изменился, исходный логический объект заменяется pointer JSON.
8. Записанный pointer проверяется по размеру и content type.
9. Объект и refcount сохраняются в SQLite transaction.

Такой порядок не удаляет единственную доступную копию данных. Если загрузка blob завершилась ошибкой, source остаётся прежним. Если source изменился во время хеширования, pointer не записывается, а новый контент будет обработан в следующем scan. Ошибка одного объекта записывается в report и log, сканирование продолжается.

Удаление blob с ref_count = 0 осуществляется только в pointer режиме и только если проход завершился без ошибок обработки объектов. Из кэша выбираются blobs с `ref_count = 0`. Сначала удаляется объект в S3 хранилище, затем удаляется запись объекта в кэше, причём SQL delete дополнительно проверяет, что refcount всё ещё равен нулю. Если blob снова получил ссылку, то запись в кэше не удалится.

## Восстановление после сбоя

Алгоритм рассчитан на повторный запуск:

- Сбой до загрузки blob не изменяет S3.
- Сбой после загрузки blob, но до замены source оставляет исходный object доступным; следующий scan увидит существующий blob и продолжит операцию.
- Сбой после записи pointer, но до записи в кэш восстанавливается при следующем scan: pointer читается, проверяется его blob и reference регистрируется заново.
- SQLite transaction либо полностью фиксирует refcount и object record, либо откатывается.
- Повторный проход не создаёт новый blob для того же `(bucket, hash)`, а уже зарегистрированные неизменившиеся объекты пропускаются.

Эти сценарии проверяются unit tests scanner/cache, включая повторный scan и имитацию частичных S3/cache failures. Удаление blobs с ref_count = 0 не запускается после прохода с ошибками, чтобы неполный листинг не привёл к преждевременному удалению данных.

## Служба и корректное завершение

Для интеграции с Windows Service Manager и systemd используется `github.com/kardianos/service`. Команда `install --config` регистрирует абсолютные пути к executable и config, а service manager запускает скрытый `service-run`. Запуск службы открывает config, S3 client, logger и SQLite, затем немедленно выполняет первый scan и ждёт `schedule.scan_interval` перед следующими.

`Program.Start` подготавливает приложение и запускает цикл в goroutine, чтобы выполнить протокол service manager. S3 health check ограничен 20 секундами; startup error возвращается service manager, записывается в configured log и системный журнал. `Program.Stop` отправляет сигнал остановки и ожидает завершения текущего scan. После него закрываются SQLite и logger, поэтому служба не завершается посередине безопасной последовательности операций. Второй сигнал завершает выполнение по <-ctx.Done() принудительно.

## Отчёт

После прохода формируется JSON report с временем начала/окончания, числом обработанных objects, уникальных blobs, duplicates, relinked objects, errors и оценками освобождаемого/освобождённого места. `bytes_reclaimed` отражает изменение текущего pointer scan с учётом созданных blobs, размера pointers и удаленных blobs с нулевым счетчиком ссылок. Текущий `bytes_reclaimable` рассчитывается по числу ссылок и размеру уникального содержимого, поэтому является оценкой общей дедупликационной экономии и может оставаться ненулевым после pointer scan.

## Известные ограничения

1. Реализован только SQLite backend; LevelDB отсутствует.
2. S3 client настроен на HTTP (`Secure: false`); HTTPS endpoint пока не поддерживается.
3. Нет cross-bucket дедупликации и общего blob bucket.
4. Формат ссылки не является прозрачным для обычного S3 клиент.
5. Pointer mode использует временный файл, поэтому требует локальное дисковое пространство, сопоставимое с суммарным размером объектов, одновременно обрабатываемых workers.
6. Нет distributed lock; несколько экземпляров не должны одновременно обрабатывать один scope и общий cache.
7. Статистика `bytes_reclaimable` не различает потенциальную экономию и текущее состояние хранилища.
8. Удаление объектов не расчитано на включенный versioning хранилища
